# Черновик карточки товара для B2B-магазина КИП

Прототип сервиса, который по данным о контрольно-измерительном приборе готовит черновик карточки товара:

- SEO-заголовок до 70 символов;
- SEO-описание на 800–1200 символов;
- таблицу характеристик, где у каждого значения указан источник;
- 3–5 поисковых запросов;
- справку для менеджера: кому подходит прибор и какие задачи решает;
- список того, что нужно уточнить у поставщика, и того, что стоит проверить перед публикацией.

Сервис работает с любой LLM через OpenAI-совместимый API: OpenAI, OpenRouter или локальной моделью в Ollama.

## Быстрый старт

Нужен Python 3.10 или новее.

```bash
python -m venv .venv
source .venv/bin/activate          # Windows: .venv\Scripts\activate
pip install -r requirements.txt
cp .env.example .env
```

Дальше выберите модель в `.env`. Проще всего запустить её локально, без ключа. Для этого установите [Ollama](https://ollama.com) и скачайте модель:

```bash
ollama pull qwen2.5:7b
```

Чтобы работать через OpenAI или OpenRouter, раскомментируйте нужный вариант в `.env` и впишите ключ.

Карточка для одного товара печатается в консоль в формате Markdown:

```bash
python -m card_generator examples/input/manometer_dm02.json
```

Можно обработать несколько товаров и сохранить для каждого файлы `.md` и `.json`:

```bash
python -m card_generator examples/input/*.json --out examples/output
```

Флаг `--json` печатает JSON вместо Markdown.

Веб-форма для контент-менеджера:

```bash
uvicorn card_generator.web:app
```

Откройте http://127.0.0.1:8000. Там же работает API: `POST /api/cards` принимает тот же JSON, что и командная строка, и возвращает карточку в JSON.

Так выглядит форма с карточкой манометра DM 02: [docs/web-form.jpg](docs/web-form.jpg).

## Входные данные

```json
{
  "name": "Манометр показывающий DM 02",
  "manufacturer": "Манотомь",
  "specs": {
    "диапазон измерений": "0–1,6 МПа",
    "класс точности": "1,5",
    "присоединение": "G1/2",
    "диаметр корпуса": "100 мм"
  },
  "description": "Прибор предназначен для измерения избыточного давления..."
}
```

- `name` обязателен: без названия карточку не собрать.
- Нужны `specs` или `description`, хотя бы одно из двух. Без них модели не на что опереться.
- Если пропущен `manufacturer`, в карточке будет «данных нет». Угадывать производителя по модели прибора сервис не станет.
- Значения в `specs` — строки или числа. Пустые значения, `null`, «—», «н/д», «не указано» считаются незаполненными: в таблице появится «данных нет», а в списке на уточнение — отдельный пункт.
- Лишние поля не используются, но сервис о них предупреждает.

## Что получается на выходе

Готовые примеры лежат в [examples/output](examples/output). Структура JSON такая:

```json
{
  "product": "Манометр показывающий DM 02",
  "seo_title": "...",
  "seo_description": "...",
  "specs": [
    {"name": "Диапазон измерений", "value": "0–1,6 МПа", "source": "input"},
    {"name": "Степень защиты", "value": "IP65", "source": "description"},
    {"name": "Температура измеряемой среды", "value": "данных нет", "source": "missing"}
  ],
  "search_queries": ["..."],
  "commercial": {"audience": ["..."], "tasks": ["..."]},
  "to_clarify": ["..."],
  "warnings": ["..."]
}
```

- `source` показывает, откуда взято значение: `input` — из входных данных, `description` — дословно из текста описания, `missing` — данных нет.
- `to_clarify` — что уточнить у поставщика: пустые поля, характеристики, которых не хватает для этого типа прибора, противоречия во входных данных.
- `warnings` — что не прошло автоматические проверки и что надо поправить руками перед публикацией.

## Как устроено

```
JSON → проверка входа → промпт → модель → проверка ответа → карточка
                                    ↑               │
                                    └─ замечания ───┘  (не больше двух раз)
```

| Файл | Что делает |
|---|---|
| `card_generator/product.py` | читает входной JSON, находит пустые и некорректные поля |
| `card_generator/system_prompt.md` | системный промпт |
| `card_generator/prompts.py` | собирает сообщения для модели |
| `card_generator/llm.py` | запрос к модели и понятные сообщения об ошибках API |
| `card_generator/checks.py` | проверка ответа: длина текстов, выдуманные числа и утверждения, рекламные слова |
| `card_generator/generator.py` | цикл «запрос → проверка → исправление» и сборка карточки |
| `card_generator/card.py` | формат ответа модели и итоговой карточки, вывод в Markdown |
| `card_generator/__main__.py`, `web.py` | командная строка и веб-форма |

## Как сервис не даёт модели выдумывать

Это главное требование задания, поэтому защита устроена в несколько слоёв.

1. **Характеристики из `specs` переносит в таблицу код, а не модель.** Исказить их модель не может, даже если очень захочет.
2. **Характеристику из текста описания модель может добавить, только если её значение написано в описании слово в слово.** «IP65» из фразы «степень защиты IP65» пройдёт, а «IP67» или «1,6 кПа» вместо «1,6 МПа» — нет. Всё, что не нашлось, в карточку не попадает и оказывается в предупреждениях.
3. **Любое число в текстах модели должно встречаться во входных данных.** Почти любая выдумка вроде IP65 или «до 120 °C» содержит число, на нём она и попадается. Типовые «утверждения» — гарантия, ГОСТ, сертификаты, поверка, Госреестр, взрывозащита, пищевое производство, агрессивные среды — дополнительно проверяются по словам: упоминать их можно, только если они есть во входных данных.
4. **Если важной для прибора характеристики нет, модель называет только её название.** Значение «данных нет» ставит код, и тот же пункт уходит в список на уточнение.
5. **Промпт прямо запрещает «типичные для таких приборов» значения.** Ещё он запрещает угадывать производителя и выбирать между противоречивыми данными: противоречие уходит в список на уточнение.

Если ответ нарушает правила или не укладывается в длину, он возвращается модели с конкретным списком замечаний, например «SEO-описание короче 800 символов (сейчас 640): сохраните написанное и допишите ещё примерно 260 символов — по предложению о каждой характеристике и о том, где применяется прибор». Попыток исправления две. Всё, что не исправилось, попадает в «Проверьте перед публикацией», а не молча в текст.

## Промпт и принятые решения

Промпт лежит в [card_generator/system_prompt.md](card_generator/system_prompt.md), а данные о товаре передаются отдельным сообщением в виде JSON. Основные решения:

- **Модель пишет тексты, а проверяет их код.** Языковые модели не умеют считать символы и охотно дополняют данные «типичными» значениями. Поэтому длины, число запросов, числа, типовые утверждения и рекламные слова проверяются детерминированно. Модели возвращается не «сделай лучше», а конкретная претензия.
- **На исправлении модель присылает только изменённые поля.** Они накладываются на предыдущий ответ. Так маленькие модели не портят то, что уже было верно, а раунды проходят быстрее.
- **Без few-shot-примеров с числами.** Пример с конкретными характеристиками модель переносит в чужие карточки, а это ровно то, от чего мы защищаемся. Вместо примеров в промпте описано каждое поле и структура описания.
- **Длина задана абзацами и числом предложений.** Описание — это три абзаца: что за прибор, его характеристики, где применяется, всего 12–15 предложений. Предложения модели считают куда лучше, чем символы.
- **Какие характеристики важны, решает модель, а значение «данных нет» ставит код.** Для механического манометра «питание» не нужно, для датчика давления оно обязательно. Жёсткий список на все приборы сразу давал бы бессмысленные строки.
- **Ответ — JSON, его структура проверяется через pydantic.** Включён JSON-режим API. Ответ, обёрнутый в markdown или с текстом вокруг, тоже принимается.
- **Температура 0,3.** Тексты получаются не шаблонными, а модель меньше фантазирует.
- **Лимит ответа — 2500 токенов.** Карточке хватает 1000–1500. Маленькие модели в JSON-режиме иногда зацикливаются и повторяют текст до конца контекста: без лимита такой ответ на ноутбуке шёл больше десяти минут, а на платном API стоил бы денег. С лимитом ответ обрывается и уходит модели на исправление. Reasoning-модели OpenAI не принимают ни температуру, ни этот параметр, поэтому оба можно оставить пустыми.
- **Используется OpenAI-совместимый API.** Один и тот же код работает с OpenAI, OpenRouter и локальной Ollama, так что для проверки задания платный ключ не обязателен.
- **Промпт хранится в отдельном Markdown-файле.** Его удобно читать и править без программиста. Лимиты в промпт подставляются из тех же констант, по которым работает проверка, поэтому промпт и проверка не разойдутся.

## Ошибки и неполные данные

| Ситуация | Что происходит |
|---|---|
| Некорректный JSON | ошибка с номером строки и позицией, модель не вызывается |
| Нет `name` или нет ни `specs`, ни `description` | ошибка с объяснением, модель не вызывается |
| Поле не того типа (например, `specs` строкой) | ошибка с названием поля |
| Пустые значения, «—», «н/д» | «данных нет» в таблице и пункт в «Что уточнить» |
| Файл не в UTF-8 (например, в Windows-1251) | просьба пересохранить файл в UTF-8; UTF-8 с BOM читается как обычный |
| Строка формы без двоеточия | ошибка с текстом этой строки, ничего не теряется молча |
| Неверный ключ, неизвестная модель, нет связи, таймаут, лимит запросов | сообщение о том, что именно проверить; временные сбои SDK повторяет сам |
| Модель зациклилась и пишет бесконечный ответ | ответ обрывается на `LLM_MAX_TOKENS` и уходит модели на исправление |
| Модель вернула не JSON или не ту структуру | ответ уходит модели на исправление; если не вышло, выводится ошибка |

Командная строка завершается с кодом 0, если всё в порядке, 1 — если часть товаров не обработана, и 2 — при ошибке настройки. Веб-API отвечает 422 на некорректный вход и 502, если не ответила модель.

Примеры некорректного входа лежат в [examples/bad](examples/bad):

```
$ python -m card_generator examples/bad/*.json
examples/bad/broken.json: Некорректный JSON в строке 2, позиция 1 (Expecting ',' delimiter)
examples/bad/no_name.json: Не заполнено название товара (name): без него карточку не собрать
examples/bad/nothing_to_describe.json: Нет ни характеристик (specs), ни описания (description): модели не на что опереться
```

## Тесты

```bash
pip install -r requirements-dev.txt
pytest
```

Тесты не обращаются к настоящей модели. Модель заменяет заглушка с заранее заготовленными ответами, а ошибки API проверяются на локальном HTTP-сервере, который отвечает кодами 401 и 404.

## Ограничения и что можно улучшить

- **Числа проверяются без единиц измерения.** Выдуманные «100 °C» пройдут проверку, если во входных данных есть «100 мм», а «гарантия 2 года» — если где-то есть «G1/2». Числа словами («два года») и «1 000» с пробелом не распознаются. Следующий шаг — сверять пару «число + единица».
- **Выдумки без цифр ловят только промпт и короткий список слов-«утверждений».** Пример выдумки, которая пройдёт, — «корпус из латуни». Можно добавить словари материалов, стандартов и видов исполнения и сверять их упоминания с входными данными.
- **Значение из описания переносится дословно, в том падеже, в каком написано.** Например, «нержавеющей стали». Это осознанная плата за то, что модель не может подменить значение пересказом.
- **Список важных для прибора характеристик составляет модель.** Он бывает неполным и меняется от запуска к запуску. Для настоящего каталога надёжнее шаблоны по категориям (манометры, датчики давления, термометры), тогда «данных нет» станет предсказуемым.
- **Дубли характеристик ищутся грубо, по первым буквам слов.** «Тип выходного сигнала» верно склеится с «Выходным сигналом», но и «Производительность» будет считаться дублем «Производителя».
- **Поисковые запросы придумывает модель, данных о частотности у неё нет.** Можно подключить Яндекс Вордстат и выбирать запросы по реальному спросу.
- **Качество текста сильно зависит от модели.** Локальная qwen2.5:7b часто не дотягивает описание до 800 символов даже после исправлений, и такие места отмечены в «Проверьте перед публикацией». Облачные модели пишут заметно лучше. Модели на 12B и больше локально стоит запускать, только если у компьютера от 32 ГБ памяти: на ноутбуке с 16 ГБ gemma3:12b вешает систему.
- **Это прототип.** В нём нет пакетной обработки каталога, кэша и очереди, а веб-форма ждёт ответа модели синхронно. Тексты не проверяются на уникальность и орфографию.

## О примерах

В [examples/input](examples/input) лежат два товара. Первый — манометр DM 02 из текста задания; там его описание обрезано, поэтому я дописал типовую фразу о назначении. Второй — преобразователь давления. В нём специально оставлены пустые поля (производитель, питание), характеристики, которые есть только в описании, и противоречие между характеристиками и описанием по выходному сигналу. На нём видно, как сервис ведёт себя на неполных данных.

Карточки в [examples/output](examples/output) сделаны локальной моделью qwen2.5:7b через Ollama на MacBook Pro M1 Pro с 16 ГБ памяти, по одной-три минуты на товар. Выдуманных характеристик в них нет. Но модель маленькая, и это видно: тексты шаблонные и местами повторяются, а противоречие по выходному сигналу во втором товаре она в этот раз не заметила. Рекламные слова и необоснованное «гарантирует», которые модель не исправила за два раунда, сервис вынес в «Проверьте перед публикацией». Чтобы пересобрать примеры на другой модели, поменяйте `.env` и запустите:

```bash
python -m card_generator examples/input/*.json --out examples/output
```
